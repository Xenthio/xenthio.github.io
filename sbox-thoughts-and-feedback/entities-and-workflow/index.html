Entities and workflow

Back to index. Audience and direction.

God, I really feel like I'd personally want the entities back. But I know that's such a personal preference, and some people really disagree with me on it.

I've often had responses in the Discord saying I'm just used to the weird way of working, or that entities actually sucked. It's also been said they worked for me because I mostly make first-person shooters, which is completely fair.

That's why these concerns are in their own section. I've said them over and over, and people don't really want to hear them again lol. I don't think it's feasible to throw out all the scene system work. I think there's a better compromise; I just don't know exactly what it is.

Code, definitions and ownership

I'm a programmer, not an artist. I get why prefabs are easier for an artist to go in and modify. But I preferred everything being in code, and that wasn't a problem because code would hotload immediately. Updating code was already updating things at runtime.

I could go into Visual Studio and change something. I didn't have to faff about in 10 different prefabs, manage 10 tabs or scroll through 50 components on the player prefab to edit one variable.

Making prefabs feels like writing FGD files again. I write some code, but then I have to go somewhere else and define an in-world object to make it work. Early s&box got me hooked on generating that from C# attributes. Write some code. Now there's an object. It exists. You can place it. That was awesome.

There were still two places to define how the model looked: OnSpawn and the editor representation in the attributes. But they were right next to each other and easy to manage. With an object-oriented language like C#, writing a class and then creating an instance of it just made sense to me.

Every time I make a prefab, I end up wanting to write code that doesn't really make sense as a reusable component. So I make a very specifically named component, and it sucks. I'd rather slap the code into the definition I'm already working on. Then it's like, why am I manually making this definition as well?

Scenes are cool with how universal they are. They're probably a better fit for some things that aren't Sandbox or a first-person shooter. But for the stuff I make, they feel too generic. I want to know where everything is in code. I don't like things jumping into some weird resource system for the sake of a resource system. It's moving parts I don't want.

How I used components

The funny thing is, I liked components. I don't think many people were using the original entity components as much as I was, at least from the public code I saw. Being labelled someone who just wants the old Source ways doesn't really fit how I was working.

I had my own version of those components running in a Simulate loop. I'd swap them out for different movement modes. Turn noclip on, add the flying controller, remove the old controller. You didn't need the rest of the character controller in noclip, just something applying velocity to position. That felt like a logical use of components.

I also liked that early s&box got rid of some of the old entity baggage. I didn't need to specify fly, ground, bounce or whatever the hell the old movement modes were. I'm not asking for every old restriction back.

What bothers me now is treating every object as a container first. Components feel forced into places where I just want to make a thing.

What did my ray hit?

When I think about a game from a programming standpoint, an object is something. It's a prop, a weapon, a player or an NPC. With scenes I often feel like I'm working with a shell that happens to have a model renderer and a bunch of other things inside it.

I end up forcing the root object to be the thing in question, using game objects in a weird entity-like way. That makes sense to me.

If I trace a ray from a bullet function and hit something, I want to look at something like trace.entity and know that's the thing I hit. Instead I find myself checking whether the game object is valid, looking for a player component, then figuring out whether I'm even looking at the right object in the hierarchy. It's a bunch of nonsense for what should be a simple interaction.

Of course I still need to check what kind of entity it is. What I miss is a clear place where the gameplay identity lives. It's not just about saving a line of code.

Weapon modding and TTT

Modding was one of the biggest strengths of that setup. You could derive from Weapon, set the fire rate to 10 million and override Shoot to make it spawn rockets instead. You didn't have to open a giant editor and whatever editor plugins a developer had made for their game.

When I made a weapon for Sandbox, the game mode inside s&box, it felt like entities with extra steps. There was a base gun component to derive from, but then a prefab and a resource definition to get it into the spawn menu.

I remember separate prefabs for the model in your hand, the view model in the camera and the dropped weapon, plus definitions around them. I might be mixing up the exact file count, but I remember the extra wiring very well. I've only bothered making one weapon that way. It wasn't nice.

Porting the entity-system TTT game mode to scenes made it even more obvious. I got it down to three files per weapon because I wanted to do it the proper way, and it was still a drag getting all the weapons in.

Previously I'd copy the code file, change the class name and change the things that made the weapon different. Now I was copying prefabs and pointing them at different models as well. I suppose it's artist-friendly. Some regular guy can go in and edit it. But it didn't feel modder-friendly to me.

I also remember getting dismissive responses when I suggested doing things more like entities. Being told you're doing it wrong when you're trying to make the thing work isn't fun. That's my experience of those conversations, not everyone in the Discord.

Loading a mod and finding its objects

With the old entity-system TTT, adding a new class was enough for a lot of modding. It didn't even have to live in the same namespace or assembly. We didn't have to build a whole separate modding SDK to make that basic workflow happen.

The newer resource-associated approach I've used felt narrower: add a resource and maybe code alongside it. What I wanted was also the broader kind of add-on that loads at game start and hooks into something like drawing a custom HUD. I don't know where every part of that stands now, but that was the freedom I was missing.

I don't think scenes make assembly loading or hooks impossible. I got too caught up in that when trying to explain it. The awkward bit for me was how a mod's new object became something the game knew how to find and use.

An entity derived from a weapon class already meant something when I spawned it. With prefabs, I needed a way to say which ones were weapons. My workaround was to put them in a weapons folder and treat everything in there as a weapon. At the time I couldn't quickly query all prefabs for the component I needed. Maybe that's easier now.

You still need some way to discover a list of things either way. But the class-based meaning and the way it fitted into my game felt much more direct before.

There's gotta be some outdated opinions in here. I know things have got better. What I'm trying to get across is why the workflow felt like a step backwards to me, even though the engine became more general.

I still personally want entities back. But the ready-made systems, networking and specialised tools matter beyond that preference. Those are things I want people to be able to build on, whatever sits underneath them.
